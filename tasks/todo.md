# ポストプロセス LLM の見直し（Gemma 4 E4B へ移行）+ 処理が終わらない問題

## 原因（処理が遅い / 終わらない）
- [x] Rust の生成ループが mlx-lm の約 2 倍遅かった（M5 で decode 21 tok/s vs 47、prefill 395 vs 893 tok/s）
  - 1 トークンごとに同期（パイプライン化なし）、GQA で K/V を毎回複製、因果マスクを CPU で n² 生成、
    1 トークン decode の delta 更新を op 単位で実行、KV キャッシュを毎トークン concat
  - MLX 0.25 のまま（mlx-lm は 0.32）。M5 の NAX カーネルは MLX 0.30+ かつデプロイ先 macOS 26.2+ のみ
- [x] 貪欲デコードの繰り返しループを止める仕組みがなく、`max_tokens`（議事録 2048）まで回り続け得た
- [x] Xcode 27 の Metal ツールチェーンで MLX 0.25 がビルド不能（`fence.metal`）→ アプリ自体ビルドできない状態だった

## 対応
- [x] mlx-rs 0.25 → 0.32 / mlx-sys 0.2 → 0.6（MLX 0.32）。Xcode 27 でビルド可
- [x] 共通の生成ループ `llm/decode.rs`: mlx-lm と同じ手順（最後の 1 トークン以外をチャンク prefill → 1 トークン step、
      log-prob の argmax、async_eval パイプライン）+ 繰り返しループ検出（≥16 トークンのブロックが 3 連続で打ち切り）
- [x] `llm/kv_cache.rs`: 事前確保 + in-place 書き込み、スライディングウィンドウ対応
- [x] Qwen3/Qwen3.5: SDPA のネイティブ GQA・causal マスク、Qwen3.5 の decode も Metal カーネル
- [x] Gemma 4 E4B の Rust 移植（`llm/gemma4.rs`）をデフォルトに。mlx-lm と 7 ケース中 6 件完全一致、
      残り 1 件は mlx-lm 側で logprob が完全同値（-0.75/-0.75）のトークンでの分岐
- [x] mlx-rs の `gelu_approximate` が bf16 → f32 昇格するのを発見、bf16 GELU を自前実装（decode 35 → 42 tok/s）

## モデル比較（mlx-lm, M5, 自己訂正 7 ケース + 504 字の口述 + 会議メモ 2,944 字）
| | 自己訂正 | 504 字口述 | 会議ノート |
|---|---|---|---|
| Qwen3.5-4B（旧デフォルト） | 3 件取りこぼし | 5.0s | 6.7s |
| **Gemma 4 E4B** | 全件 OK | 4.6s | 6.3s |
| Qwen3.5-9B | 全件 OK | 9.1s | 10.3s |
| Gemma 4 12B | 全件 OK | 13.8s | 15.4s |

## 効果（Rust, M5, リリースビルド）
- Gemma 4 E4B: decode 42 tok/s（mlx-lm 44）、2k トークンの prefill 1.8s（mlx-lm 1.7s）
- ボイスメモ: 5.5 分の会議音声 → 議事録 31s（1 回）、27 分 → 152s（6 回）。決定事項・担当者・期限は正確

## 残課題
- [x] デプロイ先を macOS 26.2 に引き上げ（ユーザー了承）。M5 で 1916 トークンの prefill 5.6s → 1.72s
  - M1〜M4 は MLX の実行時判定（GPU 世代 ≥ 17 のみ NAX）で従来カーネル。公式 mlx の macOS 26 wheel も同じ構成
  - CI を macos-26 に変更し、SDK < 26.2 なら失敗させる（MLX は警告だけで NAX なしでビルドしてしまうため）
- [ ] macos-26 ランナーでの CI ビルドは未検証（タグ push 時に確認）
- [ ] M4 実機での動作確認（コード上は従来経路 = これまで M5 で 14.0 ビルドとして計測した経路）
- [ ] 分割 safetensors の読み込み（Qwen3.5-9B / Gemma 4 12B を選択肢に出すため）
- [ ] Gemma の長文口述で「500ミリ秒ではなく600ミリ秒」のように訂正前の値に言及することがある（プロンプトで抑制余地）

# ボイスメモの書き起こし漏れ修正（2 回目）— PR 済み (v0.8.2)

## 原因
- v0.8.1 の修正（VAD しきい値のヒステリシス化）では足りなかった。v0.8.1 で録った 87s の実録音で、
  音量は普通（-40〜-30 dBFS）なのに Silero の確率がほぼ 0 に張り付く区間が 10 秒単位であり、
  そこが丸ごと「長い無音」として捨てられていた。しきい値ではなく VAD 自体の検出失敗。

## 対応
- [x] メモの書き起こしから VAD を外した。全サンプルをエンジンに渡し、分割は長さ制限のためだけ
      （20〜28s の範囲でエネルギー最小の 0.2s 地点。`partial.rs` の `quietest_cut` を再利用）
- [x] `Chunker` と関連テストを削除、合成 WAV での分割テスト 3 本に置き換え

## 効果（VAD なし一括デコードを基準にした文字再現率）
| 録音 | アプリの結果 | 今回 |
|---|---|---|
| メモ3（87s, v0.8.1 で処理） | 74.7% | 93.7% |
| メモ2（55s, v0.8.0 で処理） | 90.1% | 98.9% |
- Whisper large-v3-turbo でもメモ3 を全区間書き起こせ、無音由来の幻聴は出なかった

## 残課題
- [ ] Parakeet はチャンク境界の位置次第で、メモ3 の 40〜48s の句（「潰していきたいなというふうに思ってます」
      「そもそもボイスメモみたいなものだと」）を落とすことがある。Silero が 0 を返していたのと同じ区間
- [x] オーバーラップ分割を計測 → 採用見送り。TDT のトークン時刻で本来区間のトークンだけ残す方式を、
      切断位置 13 通り × 余白 0/1/2/4s で比較（基準は一括デコード、数値は脱落率の平均）:
      メモ3 は 3.5% → 3.3% / 1.3% / 1.9% と減るが、メモ2 は 0.1% → 1.2% / 1.0% / 0.6% と逆に増える
      （継ぎ目で「漏らしが多いんですよね」「なんか」が落ちる）。CER 最大値は改善せず、処理時間は +10〜55%
- [ ] 長い無音だけの録音での Whisper の幻聴は未検証

# ボイスメモの書き起こし漏れ修正 — PR 済み (v0.8.1)

## 原因
- `memo.rs` の `Chunker` が Silero の確率 0.5 を境に「発話 / 無音」を二値で判定し、
  チャンクの切れ目で「無音」側を捨てていた（末尾は 0.2s だけ残して切り落とし、
  次チャンクは次の 0.5 超えの 0.3s 前から）。語尾・言い淀み・小声は確率 0.2〜0.5 に
  落ちるため、切れ目ごとに丸ごと欠落していた。ホットキーは全音声を渡すので起きない。
- 実録音（55s, Parakeet）で確認: VAD なしの一括デコードは全文が出るが、チャンカー経由では
  「んだけど」「的というか」「見られないんだけど今のこの」が消えていた。

## 対応
- [x] VAD は「どこで切るか」だけを決め、何を残すかは決めない設計に変更。
      発話開始後のチャンクは連続（隙間なし）、音声を飛ばすのは 2s 以上の無音だけ
- [x] 無音判定を別しきい値に（開始 0.5 / 無音 0.15 のヒステリシス）
- [x] 長さ起因の切断はポーズの中央で、28s の強制切断は 22s 以降で最も静かなフレームで
- [x] プリロール 0.3s → 0.5s、長いポーズ後の末尾保持 0.2s → 0.5s
- [x] 回帰テスト `chunker_keeps_weak_speech_and_cuts_without_gaps`

## 結果
- 同じ録音で、チャンカー経由の書き起こしが一括デコードと同じ内容になった（5 → 4 チャンク）
- 既存の memo を直すには UI から再書き起こしが必要

# Voice Memo → 議事録（録音して、止めたらまとめて書き起こす）

ブランチ: feature/voice-memo-minutes

## 仕様
- 「録音開始」で 16kHz mono WAV を app data の `recordings/` に逐次書き込み（10s ごとに flush）
- 「終了」で VAD チャンク分割（15〜28s）→ タイムスタンプ付き ASR → Qwen3 で議事録化
- 長い録音は分割ノート化 → 統合（map-reduce）
- ホットキー入力とは別ストリーム。ASR ロックはチャンク単位で取るので録音中・処理中もディクテーション可
- 録音/処理中にアプリが落ちた memo は次回起動時 `interrupted` になり再処理できる

## タスク
- [x] rust-asr: `PostProcessor::chat`（system/user/thinking/max_tokens）
- [x] `database.rs`: `memos` テーブル + CRUD
- [x] `memo.rs`: MemoRecorder / Chunker / 書き起こし / 議事録生成 / 処理スレッド
- [x] commands + AppState + lib.rs 登録
- [x] フロント: tauri.ts バインディング、useMemos、MemoSection、MemoModal
- [x] 検証: cargo test（chunker, DB, minutes の分割ロジック）、実音声 E2E（say → WAV → 議事録）、npm run build

## レビュー
- cargo test（memo/database 20 件）通過、`npm run build` 通過
- 実音声 E2E（`say` 合成の会議音声、Parakeet + Qwen3-4B、debug ビルド）:
  - 90 秒: 8 チャンク / ASR 2.7s / 議事録 1 回の LLM 呼び出しで 41s
  - 15 分: 71 チャンク / ASR 15s / 分割ノート 2 回 + 統合 1 回で 79s
- UI は Tauri API をモックしたブラウザで表示確認（待機・録音中・詳細モーダル）
- 未確認: 実マイクでの録音（この実行環境はマイク入力が取れない）。`memo_recorder_writes_wav`（ignored）で確認可能
- 既知: release プロファイルの新規ビルドで mlx-sys の Metal カーネル（fence.metal）がコンパイルエラー。今回の変更とは無関係

## 追加: 後処理モデルを Qwen3.5 へ（同サイズの現行世代）
- [x] `rust-asr/src/llm/qwen3_5.rs` + `gated_delta.rs`（Metal カーネル）を新規ポート、`PostProcessor` は model_type で分岐
- [x] 既定を `mlx-community/Qwen3.5-4B-4bit` に。設定画面に Qwen3.5 4B/2B を追加（Qwen3 も選択可のまま）
- [x] 議事録・要約は思考なしで生成（Qwen3.5 は貪欲デコードの思考モードでループする）
- 検証: クリーンアップ 3 例（自己訂正・フィラー、日英）OK。議事録 E2E は 90 秒音声で 13.7s（Qwen3: 41s）、15 分で 40.7s（Qwen3: 79s）
- 未対応: Qwen3.5-9B（重みが 2 分割）。Qwen4 / 小型の Qwen3.8 はオープンウェイトなし
